# Feature: production-kanban
Add production orders with live-linked quote tickets, configurable Kanban stages, archiving, and period reports.
Branch: `feature/production-kanban` · Delivery: `feature-branch-chain` (reforecast ~3,000 total authored changed lines after T1; generated bindings excluded).
Test runner: `make test`; focused checks: `go test ./internal/store`, `go test ./...`, and `cd frontend && npm run test:i18n`.

## Specs

- **S1 — Production orders and quote tickets:** “Os usuários estão solicitando uma nova feature em que eles possam adicionar orçamentos já criados a Pedidos e adiciona-los num quadro Kanban (drag and drop) para organizar suas produções.” Create identifiable Pedidos and add existing Orçamentos as tickets. Each ticket represents one execution. Tickets remain linked to the current Orçamento, so edits remain visible; deleting an Orçamento referenced by any ticket is rejected with a clear reason. A Pedido may be completed manually; when all its tickets enter the designated completion stage, ask the user whether to complete it and record `completed_at` only on confirmation. The user later specified: “na tela de produção criar um novo pedido deve ser apenas um botão na tela, alinhado do lado esquerdo. Ao clicar no botão aparece o input flutuante para o usuário inserir o nome do pedido” Keep only a left-aligned create-order button visible on the production screen; clicking it reveals a floating input for the order name.
- **S2 — Configurable stages:** “As colunas do Kanban devem ser inicialmente: To-do, Em produção, Impresso, Concluído e Cancelado. O Usuário deve poder alterar os nomes e a ordem das colunas, além de poder criar novas colunas. Uma coluna que contenha tickets não pode ser excluída (o usuário deve ser informado do motivo)” The user added: “A configuração "Etapas do Kaban" deve ficar numa aba separada com nome de configurações. Ao lado de Relatórios” and clarified: “as configurações não devem ficar dentro dessa caixa colapsável” Seed the five stages in that order; permit renaming/reordering and adding stages; block deletion when tickets occupy a stage and explain why. The completion role survives renaming/reordering, and the user chose to protect that stage from deletion even when empty. Place stage-management controls on a separate production-workspace tab using the localized `settings.title` label (`Configurações` in pt-BR), immediately after `Relatórios`; render the controls directly as non-collapsible tab content, not inside a `details`/`summary` accordion; keep the existing stage operations unchanged.
- **S3 — Board lanes and movement:** “Um pedido é como uma Task e os itens (orçamentos são como sub-tarefas dele). Um pedido deve ocupara uma raia horizontal no quadro.” Render one horizontal lane per Pedido and move its quote tickets between stages by drag and drop; provide an icon-triggered popover to choose a destination stage for each ticket. Persist every stage transition so elapsed time can be reported, including cumulative time when a ticket revisits a stage.
- **S4 — Board filtering and sorting:** “Deve ser possível filtrar o quadro por pedidos (multipla seleção). Ordenar os pedidos por data de criação, data de atualização e outros campos disponíveis que vc achar relevantes” The user later requested: “a section de filtrar pedido está horrível. Substitua por um input de busca pelo nome do pedido, a exemplo do que foi feito na tela de orçamentos. Esse input deve ficar alinhado ao das opções de ordenamento” Replace the multi-select Pedido filter with a localized order-name search input aligned with the sort control; match the quote-screen behavior (case/accent-insensitive and filtering from three characters). Preserve sorting by creation/update date plus useful existing fields such as title and ticket count.
- **S5 — Soft deletion:** “Deve ser possível excluir um pedido, mesmo que ele já esteja em andamento. É feito um soft-delete no banco e ele não é mais exibido no kanban” Soft-delete a Pedido without deleting its tickets or stage history; exclude it from the active board. The user clarified that soft-deleted orders enter reports only as a count of canceled orders: “entram no relatório mas apenas como contagem de pedidos cancelados”. Count them in the report period by `deleted_at`; do not include per-order details or cascade-delete their quote/stage history.
- **S6 — Archiving:** “Deve haver um botão para arquivar os Pedidos concluídos, eles não aparecem mais no quadro mas deve ser possível visualiza-los através de outra tela, seus dados podem ser usados para geração de relatórios” Offer an explicit archive action only for completed Pedidos; hide archived Pedidos from the active board and retain them in a separate archive view and reports.
- **S7 — Reports:** “Deve ser possível extrair um relatório para um determinado período de tempo. O usuário deve poder sabe de cada pedido quando tempo cada orçamento ficou em cada etapa do processo (coluna do Kanban). O tempo total para concluir um pedido. Consumo de cada filamento. tempo estimado de impressão vs tempo para concluir o pedido.” Include completed Pedidos whose `completed_at` falls in the selected period and report their full lifecycle. Show per-ticket cumulative duration in each stage, order duration, current linked quote's per-filament estimated grams, and estimated print hours versus order duration. Include soft-deleted Pedidos only in the cancelled-order count, selected by `deleted_at`, not as per-order details. Assumptions: order duration is creation-to-completion; filament usage is explicitly labeled estimated because the current quote stores estimates, not actual usage; export a CSV.
- **S8 — Database and performance:** “As alterações no banco devem utilizar o sistema de migrations da aplicação” and “Investigue o schema do banco de dados afim de acrescentar índices (e outras otimizaçõe) para tornar a recuperação de dados mais rápida. Use a skill `sql-optimization-patterns` e `sqlite-database-expert`” Use additive SQLite migrations, preserve existing data, parameterize user input, and add only indexes justified by board/report/delete query shapes. Verify relevant plans with SQLite query-plan evidence.
- **S9 — Frontend and visual design:** “Evitar ao máximo a criação de componentes novos que poderiam ser aproveitador da `shadcn`.” “Para a iconografia use a lib lucide-react que já está instalada na aplicação” “Utilizar a skill `shadcn` para os componentes” “Utilizar skil `vercel-react-best-practices`” “Use as skills `web-design-guidelines` e `frontend-ui-engineering para projeto de frontend” The user chose “Configurar shadcn” and the Nova preset (CLI option description: “Lucide / Geist”): add the minimum shadcn/Tailwind setup needed, use shadcn components for reusable primitives, adapt semantic tokens to the existing Ledger dark/amber palette, and use lucide-react. Keep all three existing UI locales working. The user also requested: “AS tabs estão mostrando indicador de scroll @Captura de tela 2026-11-12 192921.png faça os ajustes para que isso não seja exibido” Hide the visible scrollbar arrow buttons beside the production tabs while preserving page scrolling. The user later requested: “Quero que a largura das tabs na tela de produção esteja limitado a largura do texto, não ficando sujeita a largura da tela como está agora. também quero que elas fiquem alinhadas a esquerda” Size production tabs to their labels, align them left, and wrap within narrow viewports without horizontal scrolling.
- **S10 — Domain documentation:** “Use a skill `domain-modeling` e atualizar a documentação pertinente” Update the domain glossary and user-facing README; record the live quote-link choice in an ADR because edits affect existing production tickets and historical estimates.
- **S11 — Clarification policy:** “Em caso de dúvida me pergunte antes de prosseguir” The following user clarifications are binding; ask again only if a new consequential product decision appears.
